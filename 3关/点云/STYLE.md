# 编写约定

这份是给自己人看的，学生不用读。记的是这一轮改下来定下来的规矩，写新小节、改旧小节都按这个来。

## 一、文档结构

**一个二级小节一个文件**，平铺在 `docs/` 下，不套子目录。`index.md` 是总览。

每页固定骨架：

```
（可折叠的目录树：README / 阶段三 / 各小节，当前页加粗）
（上一节 · 目录 · 下一节）

# 3.x 标题

## 问题 / 是什么
## 怎么解决        ← 原理，每个原理后面接对应的类
## 封装成函数      ← 各步骤的函数签名，说明 main 只按流程调用
## 任务            ← 这时候才让学生写代码
## 运行结果        ← 真实跑出来的数字
## 思考题

（上一节 · 目录 · 下一节）
```

目录树里父级、子级都列出来，读者不用回 README。

## 二、讲一个函数的顺序

先问题，再原理，再类，最后才写代码：

1. **问题**：具体现象，不用概括词。配一份能看见效果的数据（比如 `demo_room_noisy.pcd`），先用 `pcl_viewer` 看完再讲。
2. **原理**：为什么这个办法有效，因果要接上（“点只差几毫米 → 量的是同一个位置 → 这就是冗余”），不要“只差几毫米。按格子留一个点。冗余就没了”这种断开的写法。
3. **类**：说明它是个类；声明要带模板参数和继承（如 `class VoxelGrid : public Filter<PointT>;`），再给构造函数、成员函数、一段调用示例；类名后面挂官网 API 链接。
4. **封装成函数**：给函数签名，说明 `main` 里只按顺序调用，函数内部就是调现成的类，不用自己写循环。
5. **任务**：只说要做什么，不给答案。
6. **运行结果**：真实跑出来的数，附一句怎么看。
7. **思考题**。

## 三、代码约定

- `main` 只做流程：读点云 → 各处理步骤 → 存点云，每一步一行注释、一行调用。
- 每个操作封装成函数，`TODO` 放在函数体里，学生填函数体。
- 输入和中间点云由调用方创建，处理函数接收只读输入指针和输出引用；连续处理时在循环外创建容器，每帧覆盖输出。
- `TODO` 注释只写三样：**要做什么**、**参数在哪看**、**目标输出类似这样**。
- 注释里不出现 `cloud->size()` 这类 `->` 写法，也不给函数签名/调用示例——签名统一放 md，只有第一次出现的地方给。
- 未填时程序要能编、能跑，占位实现把输入原样拷贝到输出（如 `output = *cloud;`），占位打印写这一步要做什么（“把点云转成 ROS 消息”），不写“TODO 1 还没写”。
- 输出格式随意这件事要说清楚，免得学生以为有判分程序一字不差对。
- 默认读哪份数据要跟这一节的目的对上（3.3 默认就是带噪声那份）。
- 处理完存一份中间结果（如 `out/03_denoised.pcd`），让学生能 `pcl_viewer` 对比前后。

## 四、数字

- 所有“运行结果”里的数都必须实跑得到，不能估。
- 改了参数（比如 leaf 从 0.04 改 0.05），所有相关数字、代码注释里的目标值、正文里的对比，全部重跑更新。
- 原始数据 `demo_room.pcd` 和带噪声的 `demo_room_noisy.pcd` 各跑一组，对比着写。
- 用 `-DTUTORIAL_BUILD_SOLUTIONS=ON` 单独编译参考答案，使用 `./run --solution <编号>` 实测；学生架子也要单独编译运行。

## 五、语言

**不用这些词**（AI 味或英式中文）：

拦路虎、这条链子、它占多大、先看一眼、填对了应该看到、跑起来、你要做的、记住一条就够、判不准、飞点、干净的/脏的、留住、就够、代价、带（表示包含）、收（表示接收）、拷、塞、喂、砍、扔、磨、搞混、翻车、假装、长得一样、鬼影、大概率、别（命令语气）。

**换成**：接收、包含、拷贝、看、去掉、放大、判断不准、离群点、原始数据/带噪声的数据、内存占用、运行结果、任务。

**其他规则**：

- 单字显得生硬时补成双字（接收、包含、拷贝），但别机械套用，语境自然就行。
- 能用“是 A”说清，就别写“不是 B”。
- 不用“嫌烦”“忍不住”这类劝告口吻；真要禁止，写“请不要……”或者干脆不提醒。
- 标题写事实（`内存占用`、`运行结果`、`任务`），不写比喻和口语（`它占多大`、`先看一眼`）。
- 每个参数说清“取大取小各会怎样 + 常用范围 + 这里用多少”，不用“越大越稳”“越小删得越狠”。

## 六、链接

- 类链接到官网 doxygen 类页：`https://pointclouds.org/documentation/classpcl_1_1_xxx.html`
- 函数链接到 group 页带锚点，比如 `group__io.html#ga...`
- 链接文字写 `[查看官网 API]`，不写 `[API]`
- 不链教程页，也不链 GitHub 头文件

## 七、环境坑

- `pcl_viewer` 不在 ROS 的 PCL 包里，要 `sudo apt update && sudo apt install pcl-tools`（镜像里 apt 索引可能是空的，不 update 会报找不到包）。
- `ROS_INFO` 打中文会变成 `?????`，要打中文用 `std::cout`。
- LSP 找不到头文件：`catkin_make -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`，再在仓库根目录 `ln -sf build/compile_commands.json compile_commands.json`。
- 工作空间的 `setup.bash` 不要写进 `.bashrc`/`.zshrc`（工作空间一多会污染环境变量），常驻的只有 `/opt/ros/noetic/setup.bash`；跑练习用 `./run`，脚本内部自己 source。
- `roscore`、`rviz` 用 ROS 本体即可；`rosrun` 需要 source 过 ROS 才有包路径。

## 八、工作流

- 每次改完文档，先跑一遍 `grep -nE '不是|不要|别|无需|不用|没有' docs/*.md`，逐条判断能不能改成肯定句；这一步是提交前的必过项。
- 测代码在主仓库改、编译、运行。参考答案用独立目标，不覆盖学生源码，不用 `git checkout` 丢弃现有修改。
- 修改前保存当前差异；同步时逐文件检查，不覆盖体验空间已经完成的练习。
- 开发空间与体验空间同步文档、数据和公共源码，保留各自 `.git`、编译产物和输出。
- 用户在体验空间已填写的练习保留；需要调整接口时迁移已有实现，开发空间仍保留练习架子。
- 阶段四单独放在 `airhust_tutorial26_pcl_avoid_ws`，本轮不改。
